# 项目全面审查报告与优化实施计划

审查日期：2026-10-02。基线提交：`eb95bef9abf9d6a1ff2bc8500d71cab6b5f3ead3`，版本 `0.11.0`。

## 1. 结论

项目的基础架构合理：Rust 核心独立，桌面、CLI、Android 复用引擎；类型绑定、错误分类、压缩保真夹具和跨平台发布已有较完整的工程基础。无需推倒重构。

当前最需要投入的是文件安全、任务生命周期、移动端内存和交付验证。本报告列出 15 项问题（9 项 P1、6 项 P2）。部分已有测试验证的是局部模拟行为，没有验证实际跨层契约。建议先完成下面的 P1 修复，再扩大 Android 分发和推进稳定版发布。

本次没有确认需要立即停用整个项目的 P0 问题；这不等于已证明所有输入安全。没有对所有编解码依赖做独立安全审计，也没有执行 Windows/macOS/Android 全平台实机验收。

## 2. 范围、方法与验证边界

覆盖核心 PDF 分析、图片和字体处理、资源清理、目标大小搜索、输出写入、CLI、Tauri IPC/权限、Vue 队列和设置、Android/UniFFI、构建脚本、CI、发布、打包、文档及测试设计。针对高风险调用链逐段核对；这不是每一行代码均经形式化验证的声明。

使用 `tauri-project-structure` 工程约定作为分层参考。该技能本身以本仓库为范例，不能作为项目正确性的独立证据；结论来自当前代码、配置及实际运行结果。

证据分为三类：

- **已复现**：通过本次本地执行观察到问题。
- **代码确认**：调用链或配置足以确认缺陷；未声称已在目标设备复现。
- **待验证风险**：缺少性能、真实文档或平台运行数据，作为后续验证事项。

验证记录见第 6 节。审查只新增本报告，不修改产品实现。

## 3. 按优先级排列的问题

P1：应在相关功能下一次正式发布前修复。P2：应进入紧接着的可靠性迭代。各编号可直接用于 issue、PR 和验收记录。

### R01 · P1 · 临时文件清理可能删除不属于本次任务的文件，并漏掉真正的临时文件

**证据：已复现。** `crates/pdf-core/src/pdf/compressor.rs:546` 使用 `output_path.with_extension("<pid>.tmp")`，例如 `out.pdf` 对应 `out.123.tmp`；`OutputClaimGuard::drop`（同文件 `1843` 附近）却扫描 `out.pdf.*.tmp` 并逐个删除。

本次将当前 `OutputClaimGuard` 原样提取到独立 Rust 探针，在 `/tmp` 自建测试目录中验证：真实写入器命名的临时文件仍存在，而 `out.pdf.user-backup.tmp` 被删除。输出为 `actual_writer_temp_survives=true`、`unrelated_file_survives=false`。

影响：清理范围超出任务所有权，且残留文件清理承诺不成立。现有 `claim_guard_sweeps_stranded_temp_siblings` 测试使用了与写入器不同的命名，因此没有发现该问题。硬终止进程不会运行 `Drop`，仅增加析构清理也不能解决崩溃残留。

**实施：** 用 RAII 对象持有本次实际创建的临时路径/句柄；只删除已持有的文件，取消目录前缀扫描。启动时的残留清理采用独立且可证明所有权的协议。验收必须同时覆盖实际写入器命名、同前缀用户文件、写入失败和进程终止。

### R02 · P1 · Android 前台队列缺少 Android 14+ 必需的服务类型权限

**证据：代码确认，并核对本地已有 merged manifest。** `android/app/src/main/AndroidManifest.xml` 声明 `foregroundServiceType="dataSync"`，但未声明 `android.permission.FOREGROUND_SERVICE_DATA_SYNC`。本地 debug merged manifest 只有通用 `FOREGROUND_SERVICE`，没有类型专用权限。`targetSdk=36`，`QueueWorker.doWork` 开头调用 `setForeground`。

影响：Android 14+ 启动该类型的前台服务时会遇到权限校验失败，队列不能按预期启动。已有 merged manifest 是辅助证据，本次没有重新安装 APK 实机运行。

**实施：** 补齐专用权限；在 API 34、35、36 验证队列启动、切后台和通知拒绝场景；将最终 APK 的 manifest 权限检查加入 CI。前台服务时限与 Android 16 的任务配额另作长任务测试。

### R03 · P1 · Android 在限量检查前无界读取文件，且单文件读写阻塞主线程

**证据：代码确认。** `CompressViewModel.kt:111` 在 `viewModelScope.launch` 内执行 `openInputStream(...).readBytes()`；`MainActivity.kt:179` 在 UI scope 内直接写输出。`QueueWorker.kt` 也先 `readBytes()`。FFI 的 512 MiB 限制在 `api.rs::preflight` 中，届时 Kotlin 已分配完整数组，跨 FFI 的序列化/复制也已发生。

影响：大文件或慢速云端 DocumentsProvider 可造成界面冻结；超限输入可能在得到友好错误前 OOM。512 MiB 输入上限不是移动端峰值内存上限。

**实施：** SAF 查询、读取、保存放入 `Dispatchers.IO`；先检查可信的已知大小，再用限量读取覆盖未知大小和错误声明；长期采用应用私有临时文件/分块传输，减少跨 FFI 大数组复制。设备预算应来自可用内存与实测，不应仅机械下调固定数字。

**验收：** 未知长度流、超过限制的流、慢速 provider、撤销权限、低内存设备；超限必须在完整分配之前失败，读写期间 UI 保持响应。

### R04 · P1 · Android 密码 PDF 无法进入已有的密码重试流程

**证据：代码确认。** `CompressViewModel.kt:122` 无密码调用分析；引擎在分析阶段返回 `PasswordRequired`。同方法的通用 `catch` 将状态退回 `Idle`。只有 `runCompress` 的异常分支才设置 `pendingPassword`，而它要求先拿到 `Stage.Ready` 和分析结果。

影响：需要打开密码的文件在分析阶段就被拒绝，压缩阶段的密码弹窗不可达。仅 owner 密码且允许空用户密码的 PDF 不属于这一触发条件。

**实施：** 将“待解锁输入”建为独立状态，允许尚未获得 analysis；分析与压缩共用密码错误处理。正确密码后先重新分析，再压缩；密码不进入 DataStore、WorkManager 输入或日志。验收包括缺密码、错误密码、正确密码、取消弹窗、旋转屏幕。

### R05 · P1 · Android 用户取消后可能永久停在压缩状态

**证据：代码确认。** `cancelCompress()` 调用 `compressJob.cancel()`，`PdfEngine.native` 使用 `suspendCancellableCoroutine`；协程取消传播的是 Kotlin `CancellationException`。`runCompress` 只捕获 `FfiException.Cancelled`，`finally` 只停止进度收集，没有恢复 `stage`。

影响：用户点击取消时引擎取消句柄会被触发，但页面仍可能显示 `Stage.Compressing`。原生线程稍后完成也不会通过已取消 continuation 更新 UI。

**实施：** 分清协程取消和原生错误；在当前任务仍拥有状态时恢复 Ready/Idle，并继续遵守取消异常传播；加入任务代次避免旧任务覆盖新任务。验收按用户点击取消的真实路径执行，不能只模拟 FFI 返回取消错误。

### R06 · P1 · Android 批量队列实际并发入队，单线程引擎不能限制输入内存

**证据：代码确认。** `QueueWorker.kt:89` 把整个 `requests` 列表传入 `beginUniqueWork(..., requests)`。同一个列表代表同一阶段的工作，不是逐项 `then` 的顺序链。每个 Worker 在调用单线程 `PdfEngine` 前已读取自己的完整输入。

影响：多个 Worker 可同时读取并持有大文件，之后在 native executor 前排队；与“顺序处理、可恢复”的注释和内存假设不一致。它们还共用通知 ID 42，进度可能互相覆盖。

**实施：** 用首项 `beginUniqueWork`，其余项逐个 `then`，或采用持久化单消费者。限制从读取到释放结果的整个任务生命周期。定义单项失败、取消整个批次和重试的依赖语义；验收峰值活跃读入数为 1，并模拟进程终止恢复。

### R07 · P1 · 目标大小搜索的缓存上限未限制整轮峰值

**证据：代码确认；OOM 阈值待实测。** `target_size.rs::run_probe_round` 在全部图片探测后才调用 `enforce_bitmap_cache_budget`。串行路径会先把所有解码缓存填满；并行路径的 `workers.rs::run_worker_pool` 先投递全部任务，再收集结果，结果通道还是无界 `mpsc::channel`。每个返回项都可持有完整图片缓存。

影响：`search.rs` 的 768 MiB 是轮末清理阈值，不是峰值上限。工作线程数量和输入通道容量不能限制累计结果缓存；大量高分辨率扫描页的小 PDF 仍可能消耗数 GiB。Android 与桌面两个文件同时运行时风险进一步放大。

**实施：** 引入任务级 `ResourceBudget`，解码前预留预算，超预算先逐出缓存或串行重解码；生产和消费必须交错进行。不能简单把结果通道改成有界，否则“先投递完再接收”的调度可能死锁。移动端和桌面共享机制、使用不同预算。

**验收：** 在独立子进程测量 RSS，使用多页高压缩率图像语料，覆盖串行、并行、目标搜索、两个文件同时执行；验收峰值而非只看函数返回后的缓存计数。

### R08 · P1 · 发布校验和任务没有 GitHub 仓库上下文

**证据：代码确认。** `.github/workflows/release.yml:211` 附近的 `release-checksums` 是独立 job，没有 checkout；`gh release download/upload` 既没有 `--repo`，也没有设置 `GH_REPO`。`GH_TOKEN` 只提供身份，不提供目标仓库。

影响：标准新 runner 工作目录不是 Git 仓库，该 job 无法可靠生成并上传 `SHA256SUMS`。其他 job 的 checkout 不会共享到本 job。

**实施：** 在该 job 设置 `GH_REPO: ${{ github.repository }}` 或所有调用显式传 `--repo`。用草稿 Release 验证下载、排除旧校验和、重新上传和各平台资产完整性。Android 人工签名上传后需要重新生成校验和，现有文档已说明，仍应纳入发布验收。

### R09 · P1 · Android 缺少 NDK 和原生库时构建任务可能成功跳过

**证据：代码确认。** `android/app/build.gradle.kts:94` 在没有 NDK 且没有 jniLibs 时允许进入任务，随后 `if (!ndkConfigured)` 仅打印警告并返回；没有失败。已有目录检查只判断子项非空，也没有确认两个 ABI 的 `.so` 均存在。`rustRelease` 还依赖命令行任务名是否含大小写固定的 `Release`，通用 `assemble`/`build` 不可靠。

影响：特定本地配置下可能产出缺少引擎或复用错误构建类型的 APK，安装后初始化失败。CI 设置了 SDK 环境，因此正常 CI 可能掩盖该分支。

**实施：** 缺少工具链且无完整预构建产物时立即失败；基于 Gradle variant 接线 Rust profile，明确 ABI 列表；发布构建不允许静默复用旧库。CI 解包 APK 校验 `.so`、ABI 和至少一次引擎初始化。

### R10 · P2 · SAF 输出不具备注释声称的原子性，失败可留下半文件

**证据：代码确认。** `QueueWorker.kt:168` 声称 provider 写入是原子的，但实现为先 `createFile`，后 `openOutputStream(...).write(bytes)`，没有失败删除。DocumentsProvider 不普遍保证原子写入；单文件保存遇到空输出流时还会静默结束。

影响：写入中断、磁盘满或 provider 失败可留下零字节/截断文件。写成功但 WorkManager 尚未记录成功时进程死亡，重试还可能生成重复输出。

**实施：** 记录本次创建的 URI，写入失败时尽力删除；空流明确报错；对支持重命名的 provider 使用临时文档提交，对不支持的 provider 明确采用“失败清理”语义。为可恢复队列持久化输出 URI/阶段，定义重试幂等性。

### R11 · P2 · 桌面取消确认不等于任务结束，分析取消会继续调度后续项

**证据：代码确认，并用前端探针复现。** `commands.rs:648` 的取消命令仅设置原子标记并立即返回；`usePdfCompressor.ts::cancelCompressionRun` 等待的却是取消命令 Promise，随后立即清除 `cancelInFlight` 和 `cancellationRequested`。此时原始 analyze/compress Promise 可能未结束。本次按真实后端语义模拟即时 cancel ACK、延迟原任务结束，观察到第二次压缩已启动，以及取消分析后第二个文件仍开始分析。

影响：新压缩可与取消中的旧压缩重叠，违背并发限制；分析队列在原始分析稍后返回后可能因为取消标记已清除而继续分析其余文件。唯一 task ID 和丢弃旧结果缓解了部分状态污染，但没有解决资源重叠。

**实施：** 保存并等待实际运行 Promise 的 settled 状态；取消后立即冻结/清空本批分析队列；用 run generation 保持旧批次取消状态。后端可提供完成通知，但前端不能把 cancel ACK 当作 join。验收 mock 必须模拟“cancel 立即成功、原任务延迟退出”。

### R12 · P2 · Linux 上大小写不同的合法文件被误去重

**证据：前端探针已复现。** `usePdfCompressor.ts::addSourcePaths` 与恢复设置映射对整个路径使用 `toLowerCase()`。向 composable 传入 `/tmp/A.pdf` 与 `/tmp/a.pdf` 两个路径后，观察到只建立一个队列项。两者在 Linux 的常见文件系统上可代表不同文件；探针 mock 了分析接口，没有依赖实际 PDF 内容。

**实施：** 不在前端强制大小写折叠；短期按原始规范化路径比较，长期由后端提供文件身份/规范路径。验收 Linux 大小写不同文件、相对与绝对路径、符号链接以及 Windows 路径。

### R13 · P2 · 输出提交前缺少序列化后的取消检查

**证据：代码确认。** `compressor.rs:488` 在 `serialize_and_count` 之前检查取消，`522` 附近直接写文件；注释声称覆盖序列化期间取消，但两者之间没有再次检查。

影响：取消发生在较长序列化期间时，仍可能提交输出；前端又丢弃迟到成功结果，用户会看到已取消但目录出现文件。目标搜索也可能已有中间物化产物，需要明确取消时是否保留它们。

**实施：** 在序列化后和最终 rename 前设置提交边界，统一取消结果与文件清理策略。通过可控写入/序列化钩子验证竞态，避免依赖随机 sleep。

### R14 · P2 · 配置保存的删除后重命名回退可能丢失旧配置

**证据：代码确认。** `src-tauri/src/commands.rs::write_preset_config_at` 和 `crates/pdf-core/src/quick_profile.rs:120` 在任何 rename 错误后都删除旧文件，再重试；没有区分操作系统和错误原因。输出写入也复制了这段策略。

影响：第一次替换失败后，第二次也失败或中途进程退出，旧配置已被删除。“原子保存”的注释不覆盖这一分支。多个异步保存还需要防止旧请求迟到覆盖新请求。

**实施：** 收敛为一个经过平台验证的替换原语，失败时保留旧值；必要时使用备份恢复和目录同步。对配置更新串行化或带版本号。验收 Windows 文件占用、只读目标、第二次替换失败、并发保存。

### R15 · P2 · 队列持久化只校验外层结构，异常字段可打断恢复

**证据：代码确认，字段规范化异常已用探针复现。** `readPersistedQueue` 仅确认 `settings` 是对象；后续 `normalizeSettings` 对 `outputDir` 调用 `.trim()`，`outputDir: 123` 会抛错。`restorePersistedQueue` 以 `void` 调用，没有覆盖整个恢复链的异常处理。探针直接验证规范化函数；完整启动恢复异常未另做 UI 实机复现。

**实施：** 增加版本化存储 schema 和逐字段运行时校验，坏条目单独舍弃并提示，其余继续恢复；枚举、布尔值、数值和字符串都要规范化。将队列持久化监听从深度观察进度状态改成只观察待保存字段，避免每次进度更新触发全队列遍历。

## 4. 其他风险与工程评价

| 领域 | 已有优点 | 下一步重点 |
| --- | --- | --- |
| 核心分层 | core 独立；CLI、桌面、FFI 复用；settings 集中 | 将预算和任务生命周期做成共用机制，避免平台各自补丁 |
| PDF 保真 | 无收益不输出；SMask、CMYK、JPX、JBIG2、字体/资源保守跳过；有 Poppler 测试 | 加入真实来源文档矩阵、视觉与文本双重核对；不把文件变小当成正确性证据 |
| 资源安全 | 输入、像素、流解压、字体流均有限制 | 多流累计预算、整个任务峰值与取消时延；单项上限不能替代总量约束 |
| 桌面安全 | CSP、输出打开白名单、收窄 capability、密码不持久化 | 自定义 app commands 未采用显式 ACL；需按窗口和命令评估，但未发现可直接证明的远程利用链 |
| 前端 | 类型生成、错误本地化、队列与 UI 分离 | 拆出调度、持久化、设置职责；保留公开 API，按缺陷修复逐步拆分 |
| Android | 独立原生 UI、WorkManager、DataStore、UniFFI 类型契约 | Kotlin 生命周期、SAF、权限、低内存和 APK 运行验证明显不足 |
| CI/发布 | 多平台引擎测试、MSRV、依赖审计、绑定 freshness、Actions SHA 固定 | 发布应关联同一提交的质量结果；Android 增加运行测试、依赖更新和 ABI/绑定验收 |
| 依赖与构建 | Cargo/pnpm 锁文件；原生重依赖 feature 门控 | Gradle 依赖锁/verification metadata、wrapper SHA256、固定 NDK/cargo-ndk、构建脚本 `--locked` |
| 文档 | 开发、测试、用户指南与路线图齐全 | 测试数量和 IPC 数量已有漂移；原子性、顺序队列、内存上限等注释应与实现核对 |

以下事项属于待验证风险或产品取舍，不作为已复现缺陷计算：

1. **签名 PDF。** 引擎会重写整个文档，现有代码未见数字签名专门识别/提示路径。需用 `/ByteRange`、签名字段和 DocMDP 样本验证，明确输出可能使签名失效的行为。PDF/A 不保证合规已有文档，不应把它误报为承诺未兑现。
2. **深层解析与累计解压。** 512 MiB 是单流限制；多个 object/xref/content 流、复杂递归图仍需 fuzz 和内存/时间预算验证。`catch_unwind` 不可恢复进程 OOM、原生崩溃或所有栈溢出。
3. **取消时延。** PDF 加载、第三方编解码、字体处理、序列化有不可中断区间。先测量 p95/p99，再决定是否引入独立 worker 进程，不能承诺仅靠 AtomicBool 实现立即终止。
4. **Android 输出与恢复。** SAF 权限被撤销可能产生 `SecurityException`；现在持久化授权失败被吞掉，队列恢复假设需要验证。快速分享新文件时也要检查旧 analyze/compress 是否可能覆盖新状态。
5. **交互适配。** 桌面最小窗口为 1200×800；需验证 1366×768、高 DPI、键盘导航、屏幕阅读器、长中文路径和大量队列项。没有本轮视觉走查证据，不对界面质量作武断评分。
6. **供应链状态。** 本轮检查了 audit 配置，没有拉取最新漏洞数据库，不能得出“当前依赖零漏洞”。未做 OS 签名是已明确说明的交付取舍，应结合分发规模安排，不作为代码缺陷。

## 5. 优化计划与实施要点

以下为单名熟悉项目的工程师估算，包含必要回归测试；跨设备验收、第三方 provider 和发布等待另计。先修正确性，再以基准数据决定性能投入。

| 阶段 | 内容 | 预计工作量 | 退出条件 |
| --- | --- | --- | --- |
| A：发布前修复 | R01 文件所有权；R02 权限；R04/R05 密码与取消；R08/R09 交付错误 | 4–6 人日 | 对应回归全部通过；API 34+ 队列可运行；APK 含正确引擎；草稿发布有完整校验和 |
| B：资源与调度 | R03/R06/R07；R11/R13；SAF 错误处理 R10 | 6–10 人日 | 读入受限、任务全生命周期受控；大扫描件峰值满足设备预算；取消不会启动后续队列项 |
| C：持久化与兼容 | R12/R14/R15；真实 PDF 与 provider 矩阵；签名提示策略 | 4–6 人日 | 跨平台路径、损坏配置、写入失败、签名文件行为均有可执行验收 |
| D：性能与可维护性 | 基于数据优化缓存、采样、进度；拆分大模块；完善可复现构建与文档 | 5–8 人日 | 有可重复性能报告和回归阈值；拆分前后公开契约一致 |

### 5.1 建议的 PR 边界

1. **文件写入所有权**：先加实际 writer 与 guard 的联合回归，修清理范围与提交/取消边界。与配置替换原语可分两个 PR，避免把跨平台替换策略和任务清理混在一起。
2. **Android 状态机**：加入 Reading / Analyzing / AwaitingPassword / Ready / Compressing / Cancelling / Done；任务句柄和 generation 统一管理。先修流程，再拆 UI 文件。
3. **Android 队列和 SAF**：工作依赖图、限量读取、错误分类、输出 URI 生命周期一起验收；单文件和队列使用相同 SAF 适配层。
4. **内存预算与 worker 调度**：先建立 RSS 基准，改生产消费调度，再引入缓存预留；保持输出 PDF 语义与目标搜索结果一致。
5. **桌面调度**：以真实 cancel ACK 行为为测试基线，分离“请求取消”和“任务结束”；随后修路径身份与持久化 schema。
6. **交付验证**：修 `GH_REPO`、原生库构建失败策略和 variant 接线；加入最终 APK/安装包的烟测。小修可以先合并，发布仍由阶段 A/B 的整体验收决定。

### 5.2 必须新增的测试类型

- **跨层契约测试**：cancel ACK 已返回但任务仍运行；分析阶段要求密码；协程取消而不是 FFI 抛错；同批多个 Worker 的读入数。
- **失败注入**：写入半途 ENOSPC/EIO、空输出流、URI 权限撤销、配置替换失败、创建输出后进程终止。
- **真实渲染回归**：文本提取一致性、页面数/尺寸、注释和表单外观、书签、透明度、CMYK/ICC、G4/JBIG2/JPX、CID/CFF 字体。指定允许有损变化的阈值，不要求所有预设逐像素相同。
- **移动端测试**：ViewModel JVM 测试、WorkManager 测试、Compose/仪器化烟测；API 26、34、36，arm64 真机至少一台，并覆盖低内存档。
- **发布物测试**：从最终安装包/APK 启动并压缩一份夹具，验证 bundled CLI、右键入口、更新验签、原生库加载与校验和。

### 5.3 性能衡量与优化顺序

建立固定语料清单：文本型、混合型、照片扫描、黑白扫描、CMYK 印刷、透明图片、多字体、加密、损坏输入，各包含小中大型。记录输入与输出哈希、页数、大小、feature 集、CPU/RAM、构建版本。

每轮记录：耗时 p50/p95、峰值 RSS、输出大小、视觉指标/文本一致性、取消延迟、目标未达比例。至少预热一次并重复运行，单独记录冷启动；不能把并行测试受负载影响的耗时当正式基准。

优先级为：消除无界缓存和重复 ByteArray → 控制文件级/图片级嵌套并发 → 减少不必要重解码/序列化 → 优化分析复用 → 调整编码器热路径。保留正确性与内存预算后，再评估更激进的缓存。

建议最初采用相对回归阈值：同机同语料的耗时或 RSS 增长超过 10% 触发人工复核，而不是直接断言不可发布。移动端的绝对内存阈值应根据测试设备确定；目前没有足够数据给出可信的统一数字。

### 5.4 架构调整的边界

保持 `pdf-core` 为业务规则来源。新增运行上下文以承载取消、预算和进度策略；Tauri/FFI 只映射平台入口。SAF 和 WorkManager 留在 Android 层，不塞入 Rust 领域模型。

`usePdfCompressor.ts` 约 1015 行，建议逐步拆出队列存储、调度器和设置逻辑；`compressor.rs` 与 `encode.rs` 的拆分以输出写入/图片任务/编解码职责为界，避免仅按行数拆文件。`pdf/tests.rs` 约 7684 行，可按字体、颜色、目标搜索、加密、保真、恶意输入分组，保留共享夹具。

在预算、平台生命周期尚未稳定前，不建议同时大规模换框架、换 PDF 库或增加更多编码格式，这会扩大验证面并推迟已知缺陷修复。
